## Logo officiel

- Source : **image fournie par l'utilisateur dans cette conversation**, non inventée. Elle a été optimisée en `static/brand/official-logo.webp` (~37 Ko, proportions 1024 × 487). Le même fichier est référencé sur les entrées publiques et réservées, l'inscription, la connexion, l'attente de validation, l'accueil, la barre latérale, les notifications, le chargement, l'écran hors ligne et le bandeau de mise à jour.
- Les images PWA (`static/icons/`) sont des **dérivés techniques** créés à partir de cette source, sans autre dessin de logo : icônes 192/512 px, version maskable, icône Apple et favicon. Les manifestes et les liens portent une URL versionnée ; le service worker met à jour sa liste de fichiers et purge ses anciennes caches publiques à l'activation.
- Une icône déjà épinglée sur Android/iOS dépend du système d'exploitation : le manifeste mis à jour ne garantit pas à lui seul son remplacement immédiat sur un téléphone déjà équipé. Vérifier physiquement les appareils et, si nécessaire, demander à l'utilisateur de retirer/réinstaller son raccourci PWA. Ce n'est **pas** une application Android/iOS native distribuée via une boutique.

## Versions et annonces

- `version.js` est la source unique du **numéro de build déployé** (`13.0.0`) ; `/build.js` fournit ce numéro à l'interface ; `/api/app-version` renvoie sans cache le build, la version publiée (si des notes approuvées existent), la version minimale en cas de mise à jour obligatoire, le titre, la date, le type, le motif et les listes de nouveautés/corrections déclarées. Aucune annonce n'est préremplie ou inventée.
- Migration PostgreSQL additive **011** : table `app_releases` ; SQLite de développement suit le même schéma. Aucune table de comptes, documents ou résultats n'est vidée. Dans « Mises à jour », accessible **au chef seulement** (vérification serveur), il peut enregistrer, modifier, dater, publier, retirer et revoir les notes antérieures. Publication impossible si le numéro est différent du build réellement exécuté ; une date future reporte l'affichage. Éditions/publications/retraits restent audités.
- L'interface vérifie la version périodiquement (et au retour au premier plan). Un **bandeau vert non modal** apparaît uniquement si une version **plus récente, réellement publiée et déjà déployée** possède des notes. Il présente les nouveautés et corrections enregistrées, un bouton « Mettre à jour » et « Plus tard ». Fermeture temporaire : 6 h pour une mise à jour facultative, 10 min pour une mise à jour obligatoire ; une nouvelle version se signale de nouveau. Les mises à jour obligatoires sont expliquées mais ne coupent pas l'accès aux données essentielles.
- Le bouton préserve la session web : il refuse d'interrompre un formulaire modifié non enregistré ; sinon il demande l'actualisation du service worker, active explicitement le worker en attente (`AC_SKIP_WAITING`), puis recharge la page. Sans worker (navigateur web ordinaire), il recharge la page depuis le réseau. Un message confirme la nouvelle version une fois réellement chargée. Le contenu personnel et les API ne sont jamais mis en cache par le service worker.

## Déployer et vérifier avant d'annoncer le colis comme terminé

1. Sauvegarder PostgreSQL **hors du Web Service**, garder l'ancien code et ne jamais supprimer de données. Intégrer les fichiers du delta à la racine du projet existant (colis 12). S'il est encore au colis 11, intégrer **les deux deltas dans l'ordre**. Faire un commit uniquement des fichiers du delta, sans `node_modules`, bases de tests, journaux ou secrets.
2. Conserver le Web Service Render existant : Runtime **Node.js**, `npm install`, `npm start` et la variable privée `DATABASE_URL` **déjà configurée**. Vérifier migrations et `/healthz` sans révéler la valeur de cette variable.
3. Contrôler sur le vrai domaine le logo dans `/` et `/chef`, les URL `/brand/official-logo.webp?v=13-brand`, `/build.js` et `/api/app-version` (build `13.0.0`), puis l'icône PWA sur téléphone. Le chef rédige **après confirmation du déploiement** des notes correspondant uniquement aux fonctions réellement présentes, puis les publie. Sans notes publiées, le bandeau ne doit pas apparaître.
4. Faire la recette du bandeau sur un client plus ancien **déjà équipé d'un mécanisme de mise à jour**, de la session, des formulaires et des caches après un nouveau déploiement. Une copie du colis 12 déjà ouverte ne contient pas encore ce mécanisme : elle doit être actualisée au moins une fois pour installer le code du colis 13 ; on ne peut pas rétroactivement afficher un bandeau dans du JavaScript du colis 12. Pour les futures versions, incrémenter `version.js`, changer les URL d'actifs et l'identifiant de cache du service worker, et publier les notes vérifiées après le déploiement.

**Ne pas déclarer la fonction active sur la production avant ces contrôles réels.**
